# T03 — Jev client and smoke test

Session 1, 2026-10-04. `src/jev/client.py`, `scripts/t03_jev_smoke.py`.

## What ran

`JevClient` features, each covered by a unit test (`tests/test_client.py`):

- pinned model `jev-1.13.0` in every request; `response.model` must equal `expected_response_model` or the run aborts (`ModelMismatch`);
- verbatim persistence: every request and response, request id (`x-typesafe-request-id`), client-side latency, `usage`, computed cost, state hash and cache key go to `data/raw_responses/<experiment>.jsonl`; successful responses also to the content-addressed cache `data/raw_responses/cache/<k[:2]>/<k>.json` (SHA-256 over model, bank version, state, question map; D6);
- cost = `input_tokens x 0.042 / 1e6 USD` (no cost field in the API response; D2), accumulated in `data/raw_responses/spend_ledger.jsonl` across runs; `MAX_USD` (1.0 this session) stops before the next live call;
- retries with exponential backoff on 429/529/5xx and transport errors (6 attempts, `retry-after` honoured); 401 raises `AuthError` and stops; 400/422 are logged as failed records and counted, not raised (D8);
- `--no-cache` bypass; thread-pool concurrency (`ask_many`, `concurrency` in config); latency p50/p95 from live calls only.

## Observations

- Jev's own token count is about 500 tokens above the tiktoken size of the serialised state (1,333 vs 821 mean for S1 + `q_direct`); the question and request framing account for the difference. Cost figures use the API's `usage.input_tokens`.
- Adding the 14 remaining bank questions to the request costs about 500 input tokens (+37 %) and no measurable latency: 280 ms p50 for 15 questions vs 277 ms for one. The marginal cost of a question is a few cents per 1,000 sites.
- No rate limiting was hit at 4 workers (documented limits: 80 requests/s, 100k tokens/s).
- Detection numbers from these runs are not reported: the fixture and the bootstrap samples are for building and debugging only (ground rules, CLAUDE.md).
